# Code notes

## Run
- Student (Android): `flutter run -t lib/main_student.dart`
- Admin (Web): `flutter run -d chrome -t lib/main_admin.dart`
- The apps talk to the real Firebase project `cairo-coding-app`. The in-memory fake backend is only used by tests (`fakeSourceOverrides`).

## Structure
```
lib/
├── main_student.dart / main_admin.dart   each passes its own router to bootstrap()
├── core/      theme, fonts, assets, l10n helpers, Result + errors, shared widgets, animations
├── data/      models, sources (contracts), fake/ (in-memory backend), repositories, data_providers.dart
├── shared/    screens both apps use: login, splash, blocked, preferences, routing guard
├── student/   student router + tabs (home, schedule, quizzes, recordings, profile)
└── admin/     admin router + sidebar shell + courses, course detail tabs, groups, group detail tabs, students, instructors, quizzes, settings
```
The student entry point never imports `admin/`, so admin code isn't compiled into the APK (and vice versa).

## Riverpod in this project
- **Reads are streams.** Repositories expose `watch*()` streams; screens read them through `StreamProvider`s and get `AsyncValue` (loading / data / error) for free. When Firestore arrives, these become snapshot listeners with the offline cache.
- **Derived state is plain `Provider`s**, e.g. `nextSessionProvider` and `filteredRecordingsProvider` compute from the stream providers.
- **UI state that several widgets share** is a `Notifier` (`recordingsFilterProvider`, `groupsViewProvider`, `themeModeProvider`). State only one widget cares about stays in `StatefulWidget` (e.g. the Upcoming/Past toggle).
- **Writes** call repository methods that return `Result` (`Ok` / `Err`); the screen shows a snackbar on `Err`. The streams update the UI by themselves afterwards.
- **Small rebuilds:** `ref.watch(provider.select(...))` is used where a widget needs only part of a value (e.g. the countdown is the only widget that rebuilds every 30 seconds).
- `family` providers take an argument (`groupStudentsProvider(groupId)`); `autoDispose` closes the stream when no screen is listening.

## Routing (go_router)
- `shared/routing/auth_listenable.dart` holds the one auth guard (`authRedirect`): loading → splash, signed out → login, not allowed → blocked, otherwise home.
- Student uses `StatefulShellRoute.indexedStack`, so each bottom tab keeps its scroll position.
- Admin URLs: `/courses` (home), `/courses/:courseId/:tab` (groups | sessions | instructors | students), `/groups`, `/groups/:groupId/:tab` (students | schedule | recordings), `/students` (every student, search + course filter), `/instructors`, `/quizzes`, `/quizzes/new`, `/quizzes/:quizId/edit`, `/quizzes/:quizId/analytics`, `/settings`. Refreshing the page keeps you where you were.
- Student quiz pages open on the root navigator, above the bottom tabs, so taking a quiz fills the screen.

## Theme and fonts
- Dark = the Cairo Coding brand palette. Light = derived palette with accent #7c3aed.
- Fonts are bundled in `assets/fonts` (Nunito, Cairo for Arabic, JetBrains Mono) and named in `AppFonts`.
- No ScreenUtil: fixed logical sizes, plus `Breakpoints` / `LayoutBuilder` for the admin layout.

## Arabic and English names
- Course, session and recording names are often English inside the Arabic UI. Names ending in symbols ("C++", "OOP (Encapsulation)") flip in RTL ("++C"), so they're shown through `context.bidi(name)` (`core/helpers/bidi.dart`), which wraps them in Unicode isolate marks only when their direction differs from the UI's. `ClassSession.topicLine` always isolates its names because it mixes them with translated words. Never save isolated text: in the session form the marks go on `labelWidget`, not the entry's `label`.
- `bidi()` also puts an invisible word joiner (U+2060) between the pluses of "C++", because line breaking could otherwise split it into "C+" and "+". Tests that look up a displayed name containing "C++" use `'…C++'.unbroken`.

## Firebase
- Config: `lib/firebase_options.dart` and `android/app/google-services.json` (generated by `flutterfire configure`), `firebase.json`, `.firebaserc`.
- Sources: `data/sources/firestore_academy_source.dart`, `data/sources/firebase_auth_source.dart`. They are plugged in through `data/data_providers.dart`; nothing in `student/`, `admin/` or `shared/` knows about Firebase.
- Collections: `admins/{uid}`, `users/{uid}`, `instructors/{id}`, `courses/{courseId}`, `groups/{groupId}` with `sessions`, `recordings`, `announcements`, `quizzes` and `quizBoards` subcollections, `quizzes/{quizId}` with `content/paper` and `content/key`, and `quizAttempts/{quizId}_{uid}_{number}`. Dates are Firestore Timestamps (converted in `firestore_mapping.dart`).
- Courses sit above groups: a course holds its session list in teaching order (`sessionTitles`, session n = line n) and its `instructorIds`; each group points to one course with `courseId`. Students still belong to groups, so a course's students are everyone in its non-archived groups.
- Instructors: each has a `name`, an `email` (saved in lower case), an optional `phone` and the `groupIds` they teach; the Instructors page counts only non-archived groups. Sessions store the instructor's name, not their id, so renaming an instructor also rewrites the name on every session that carries it (`renameSessionInstructor`).
- Sessions: generating from weekly slots names each new session from the course list by its number (unless it inherits an edited name). Sessions added by hand from "Add session" have `manual: true`, so regenerating never replaces them. Their link is `meetingLinkOverride`; empty means the group's link. The instructor list in the session form shows the group's and the course's instructors (everyone while neither has any).
- Offline cache is on (`persistenceEnabled`), so reopening the app reads from cache first.
- Student app listens to each of the student's groups separately (one document / subcollection listener per group). That keeps every read provable by the security rules.
- Adding students (admin): `StudentAccountCreator` signs up the new email on a second FirebaseApp, so the admin stays signed in, then writes `users/{uid}` and sends the password-reset email that works as the welcome email. An email that already has a `users` doc only gets the group added.
- Editing students (admin): "Edit student" (Students page and a group's Students tab) saves `name`, `phone`, `groupIds` and `active` with `updateStudent`. The email is shown but locked: it's the Firebase Auth sign-in, and the client can't change another user's Auth email without the Admin SDK.
- Weekly slots are Cairo local time. `SessionGenerator` converts them through `CairoTime` (Africa/Cairo, DST-aware) into real instants.
- Rules: `firestore.rules`. Admins are whoever has an `admins/{uid}` doc (only creatable from the console). Students can read their own `users` doc and the groups in their `groupIds` while `active == true`.
- Deploy rules: `firebase deploy --only firestore`. Deploy the dashboard: `flutter build web -t lib/main_admin.dart && firebase deploy --only hosting`. The hosting `predeploy` hook runs `tool/hash_icon_font.sh`, which renames the tree-shaken icon font after its content (and updates `FontManifest.json`), so browsers never show new icons blank from an older cached font.

## Attendance, views, sign-ins and announcements
Added with the dashboard redesign (Nov 2026). Like quizzes, there is no server, so each of these is a field students write about themselves and `firestore.rules` limits them to their own uid (`addsOnlySelf`).
- **Attendance** is `attendees` (uids) on each session doc. Tapping "Join meeting" adds the student from 30 minutes before the start until the session ends (`StudentActivity.joined`; the rules check the same window on the server's clock). The admin corrects it from the session's "Attendance" button. A session with no `attendees` field never had attendance taken, so it's left out of every rate (`Attendance.counted`), and sessions from before this feature don't count as everyone missing.
- **Recording views** are `viewers` (uids) on each recording, added when the student opens it. It says the student opened the link, not that they watched it all.
- **Last seen** is `lastSeenAt` on `users/{uid}`, stamped with the server time at most every 6 hours while the app is open. No stamp means the student never signed in, shown as "Invited" with a button that resends the set-password email.
- **Announcements** live in `groups/{groupId}/announcements/{id}`, one copy per group with the same id, so a student's reads stay provable per group. They show under the bell on Home; read state is kept on the phone. There is no push notification (that needs a server). "Notify students" on a new recording posts one.
- Neither `toMap()` of a session nor of a recording writes these lists, and sessions are saved with `merge`, so an admin edit never wipes attendance taken meanwhile.
- The dashboard's numbers come from `GroupInsights` (one per group) and `OverviewNumbers`. Quiz averages use the leaderboards, which hold each student's first attempt.

## Profile, tasks and certificates
The student's last tab is Profile (`student/profile/`): name and email, diploma and group, attendance rate, tasks rate and certificates, then the app's preferences and logging out. Its labels use `.tr(context: context)` so they change at once when the language is switched on that page.
- **Diploma** is the name of the course each of the student's groups points to. Students read courses one by one (`watchCourses(ids:)`); the rules allow `get` on a course to any active student but keep `list` admin-only. Archived groups show only when the student has no current one.
- **Tasks** are `taskDoneBy` (uids) on session docs, ticked by the admin from the session's "Task" button (Group › Schedule). Like `attendees`, the field missing means the session had no task, so it's left out of the rate; saving with nobody ticked means a task nobody handed in, and "No task" deletes the field. Students can't write it: their only session update is `addsOnlySelf('attendees')`. Tasks rate = sessions whose `taskDoneBy` has the student ÷ non-cancelled sessions that have the field.
- **Attendance rate** on the Profile uses the same sessions as the dashboard (`Attendance.counted`).
- **Certificates** are `certificates` on `users/{uid}`: a list of `{title, url, issuedOn}` with the date as `yyyy-MM-dd`, a nested map, so `toFirestore` doesn't convert it. The admin adds or removes them in "Edit student" (saved with the rest by `updateStudent`); the link is a Drive or PDF https link because Spark has no Storage. The student opens it outside the app.

## Quizzes
There is no server on the Spark plan, so the phone does the arithmetic and `firestore.rules` checks every step. Read the block at the top of the quiz rules before changing anything here.
- **Where things live.** `quizzes/{id}` is the admin's master copy. `content/paper` holds the questions and `content/key` the answers, in separate documents so one can be hidden without the other. `groups/{id}/quizzes/{quizId}` is what students list: a copy of the details with no questions, one per group while published, so a student's listeners stay provable by the rules. All of these change together in one batch (`FirestoreQuizSource.saveQuiz`).
- **An attempt's life.** Start: the fixed id `{quizId}_{uid}_{number}` means no duplicates and no extra attempts, and the questions become readable. Answer: rules allow one new answer at a time, never a change, and only before the deadline on the server's clock (plus 30 seconds' grace). Submit: answers freeze and the key becomes readable. Grade: the phone reads the key and writes the score, and rules recount it.
- **Why points are fixed values.** Rules have no loops, but `answers.diff(bucket).unchangedKeys().size()` counts matches in one expression. The key is stored as one map per point value (`p1`, `p2`, `p3`, `p5`, `p10`, `p20`), so a score is a short sum. Adding a value to `QuizQuestion.pointChoices` means adding it to `gradesCorrectly()` in the rules too.
- **Only the first attempt ranks.** Once a student has submitted, the key is readable by them, so a retake can't be proven fair. Retakes show on the student's own results and in analytics as "best", and never change the leaderboard.
- **Answers reach nobody early in the app.** There's no right or wrong feedback while answering, and the answer review opens only after the quiz closes. Rules alone can't stop someone with tools reading the key after their own first submit.
- **Leaderboards cost few reads.** `groups/{id}/quizBoards/{quizId}` is one document per group and quiz, with a row per student, so the overall ranking costs one read per quiz instead of one per attempt. Rules let a student add only their own row, once, copied exactly from their graded first attempt. Ties share a rank: higher score, then less time in whole seconds (`Leaderboard.rank`).
- **Nothing gets stuck.** `QuizRepository.finishAttempt` picks up from whatever state it finds and shares work between callers, so a retry, an app restart, or `quizRecoveryProvider` on the Quizzes tab all finish the same attempt. Answers save in the background and sit in Firestore's offline queue when there's no signal.
- **Time.** Rules use the server's clock. Time taken runs from the start to the last answer, so reopening the app days later doesn't count. A question's own timer is only enforced by the app; the whole-quiz limit is enforced by the rules.
- **Editing.** Only drafts can be edited, so a published quiz must be unpublished first. Once anyone has an attempt, the questions lock and only the details can change, or saved scores would stop being true. Duplicate the quiz to change questions.
- Images are https links, because Spark has no Storage. Avatars are initials, because students have no photo.

## Tests
- `tool/rules_test/`: security rules against the Firestore emulator (`npm install && npm test`): quizzes, plus attendance, views, last seen and announcements in `attendance.test.js`, and course reads, certificates and tasks in `profile.test.js`. The files share one emulator, so they run one at a time.
- `test/attendance_test.dart`, `student_activity_test.dart`, `admin_attendance_test.dart`: attendance and quiz averages, what the student app writes, and the admin's attendance and announcements.
- `test/quiz_model_test.dart`, `quiz_leaderboard_test.dart`, `quiz_analytics_test.dart`, `quiz_repository_test.dart`: scoring, availability, publishing checks, ranking and analytics. `FakeQuizSource` refuses what the rules refuse.
- `test/student_quiz_test.dart`, `student_quiz_timing_and_results_test.dart`, `admin_quiz_test.dart`: the full quiz flows on the fake backend.
- `test/routing_and_schedule_test.dart`: auth redirect rules and the session generator.
- `test/student_profile_test.dart`: the Profile tab against the fake store, and how certificates and tasks map to and from Firestore. Ticking a task is in `admin_attendance_test.dart`, adding a certificate in `admin_edit_student_test.dart`.
- `test/student_smoke_test.dart`, `test/admin_smoke_test.dart`: boot the real app, sign in, and walk through every tab.
- Admin tests open a group with `openGroup(tester, 'CS140')`: the Groups page sorts by next session, so the first card changes with the date.
